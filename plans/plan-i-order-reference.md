# Phase I: order reference (#9)

## At a glance

Every order gains a short number a person can read out over the phone, generated by the database
and never reissued. It appears in the list, leads the detail page and names the order on the
delete confirmation. The GUID stays the address; the number is only a label, so nothing in the
domain branches on it. Verified by an integration test that reads the number back from a fresh
query and by component tests on the three places it shows.

## Context

Part of [plan-bike-repair-shop.md](plan-bike-repair-shop.md), first in the roadmap's `Next up`
queue. Comes out of both manual passes: each one had to find an order by typing a customer name,
because nothing on screen identifies an order at all. The master plan settled the shape on
2026-09-21 under `The order carries a human-readable reference alongside its id`, and the roadmap
settled it against a GUID slice: a reference nobody can dictate or remember defeats the purpose of
having one.

It runs before [#10](https://github.com/filigott/bike-repair-shop/issues/10) because the reworked
detail page is meant to lead with the reference, and building that page twice is avoidable.

## Design decisions

**The database generates it, so the entity cannot stamp it.** `orders.order_number` is a `bigint`
identity column and `OrderNumber` reads 0 until `SaveChanges` returns. That is a real cost and it
is accepted: the reference is an outward-facing label, not a domain invariant. No rule reads it,
no transition depends on it, and `Place` therefore has nothing to validate about it. Generating it
in the application instead would mean either a round trip to read the current maximum, which
races, or a second sequence-like construct the database already provides.

**`BY DEFAULT` plus a unique index, not `ALWAYS`.** `GENERATED ALWAYS` would refuse an explicit
value outright, which is the stricter reading of "never dictated". It also refuses a future import
or backfill, which is the likelier need in a shop that has paper records. The unique index gives
the guarantee that matters without closing that door.

**It starts at 1000.** A four-digit reference reads as a real one and holds its width for the life
of this application. Starting at 1 makes the first orders look like test fixtures.

**The wire carries the number, the UI carries the format.** The API returns `orderNumber: 1042`
and the front end renders it through `orders.reference`, so the `#` prefix is presentation rather
than contract, and the column stays sortable and right-alignable. The interpolation must stay
plain `String(n)`: `Intl.NumberFormat` under `nb-NO` renders 1042 as `1 042`, which is a different
thing to read out loud than what the database holds. This is the invariant-culture rule for
identifiers seen from the rendering side.

**The number is never reused.** The demo reset runs `ExecuteDeleteAsync`, which leaves the
identity sequence where it stands, so a reset issues 1027 onwards rather than handing 1000 to a
different bike. Deliberately not restarted: a reference someone wrote on a job card must not come
back attached to another order.

**The GUID stays the route key.** `/orders/{id}` and every endpoint keep addressing by `Id`. The
system addresses by the GUID and labels by the number; swapping the key would be a contract break
across the generated client for no gain, and a label that is also a key invites someone to guess
one.

**Search waits for [#4](https://github.com/filigott/bike-repair-shop/issues/4).** Matching a digit
string against both a phone number and an order number is a search design question, and the
current predicate already conflates the two if a numeric branch is bolted on here.

## Steps

**I1. Column, entity property and both DTOs.** `public long OrderNumber { get; private set; }` on
`MaintenanceOrder`, mapped in `MaintenanceOrderConfiguration` with `ValueGeneratedOnAdd()`, the
Npgsql identity-by-default configuration seeded at 1000, and a unique index. One migration. Both
`MaintenanceOrderSummary` and `MaintenanceOrderResponse` carry `OrderNumber`, projected through
their existing `From` factories.

Tests: an integration test that places an order over HTTP, re-queries from a fresh scope and
asserts the number came back non-zero, plus a second order asserting the numbers differ and
ascend. The unit suite needs nothing new, because the entity gains no behaviour.

The migration was verified against the dev database rather than assumed. Its 26 demo rows came out
numbered 1000 to 1025 and the unique index created in the same transaction, so no backfill step is
needed. The detail is in [reference/verified-on-this-machine.md](reference/verified-on-this-machine.md).

**I2. The number in the UI.** Regenerate `openapi.generated.ts` first, which needs the API
listening on 5260 and is therefore a handoff rather than something this session runs. Then a
leading `Order` column in `orders-table.tsx`, the detail page heading becoming the number with the
customer name beneath it, and `orders.delete.confirm` naming both. Keys `orders.reference` and
`orders.columns.reference` land in `en.json` and `nb.json` in the same commit.

Tests: the existing route tests cover all three surfaces already, so the additions are assertions
on them rather than new files.

Ends with a manual pass: place an order, confirm the number appears in the table and on the page,
reset the demo data and confirm the numbering continues rather than restarting.

## Out of scope

- Searching or sorting by the number (#4).
- The detail page layout itself (#10). This step puts the number at the top of the page as it stands
  and leaves the three always-open forms alone.
- Barcodes, printable job cards, any per-year or per-branch prefix scheme.

## Open questions

None. The four opened at the start of the session were settled the same day: identity column from
1000, raw number on the wire, the number in all three UI surfaces, and search deferred to #4.
